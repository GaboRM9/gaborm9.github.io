Giving an agent a fetch tool without opening your network

2026-10 · from the orbz codebase

A fetchUrl tool looks harmless: take a URL, return some text. But the URL comes from a model, and the model reads untrusted pages. A malicious page can tell it to fetch http://169.254.169.254/ (cloud metadata) or something on your internal network. That is server-side request forgery (SSRF).

Check the address, not the string

Blocking the text "localhost" is useless: 0x7f.1, [::ffff:127.0.0.1] and a hostname that resolves to a private IP all get through. orbz resolves the host and checks every address it returns:

  • IPv4: 0/8, 10/8, 127/8, 100.64/10 (CGNAT), 169.254/16 (link-local and metadata), 172.16/12, 192.168/16, 198.18/15, multicast and above.
  • IPv6: loopback, unique-local, link-local, multicast, plus IPv4-mapped, IPv4-compatible and NAT64 forms that smuggle a v4 address inside.
  • Anything that isn't a valid IP after resolution is refused.

Redirects are the second door

A public URL can redirect to a private one. So redirects are followed manually, at most 3 hops, and each hop goes through the same check:

const res = await fetch(u, { redirect: "manual", signal: AbortSignal.timeout(8000) });

Cap what comes back

The body is read in a stream and stops at about 64 KB, then trimmed to 2000 characters for the model. A huge response can't exhaust memory, and the model gets a small, predictable amount of untrusted text.

The gap I left open

DNS can change between the check and the connection (rebinding). The fix is to pin the resolved IP in a custom dispatcher. I left a comment in the code instead of building it, because the fetch tool is also behind an approval gate. If this ran unattended, I'd close that gap first.

Test it like an attacker

The test suite checks private, loopback, metadata and mapped IPv6 addresses. Redirect handling is not covered by a test yet, which is the next thing I would add.
