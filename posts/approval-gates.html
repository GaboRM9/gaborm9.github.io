Approval gates for agents: ask before the side effect

2026-10 · from the orbz codebase

An agent that can only read is safe and a little boring. The moment it can send an email, call an MCP server or fetch a URL, every mistake the model makes becomes a real side effect. In orbz I wanted a rule that is easy to explain: if a tool reaches outside the app, a human says yes first.

One line decides

The AI SDK lets you hook the decision per tool call. orbz uses it like this:

toolApproval: ({ toolCall }) =>
  toolCall.toolName.startsWith(MCP_PREFIX) || APPROVAL_TOOLS.has(toolCall.toolName)
    ? "user-approval"
    : undefined

Every tool coming from an MCP server is prefixed mcp_, so it is gated automatically, including servers I add later. Built-in tools opt in through a small set (fetchUrl, createSkill). Calculators and time lookups run without asking, because asking about them would train people to click "approve" blindly.

The click arrives with the next request

An approval is just another message part. The chat UI shows a card, the user clicks, and the decision travels back inside the next request. The server then does two things: it executes or skips the tool, and it records the decision.

Log it once, decide it once

The same assistant message gets synced on every turn, so naive logging would write duplicates or let a later turn overwrite an earlier decision. The approvals table avoids both:

insert into approvals (...) values (...) on conflict(approval_id) do nothing;
update approvals set decision=?, ... where approval_id=? and decision='pending';

A request is stored once as pending, and a decision only applies while it is still pending. Calling the sync twice is harmless. The Runs tab then shows how many approvals are waiting.

What I'd still add

  • Per-tool "always allow" for trusted servers, with an audit trail.
  • Showing the exact arguments in a diff-like view instead of raw JSON.
  • A hard budget per run in addition to the 8-step limit.
